How to choose the next safe step in application modernization
25.11.2026
Wer eine Anwendung modernisieren will, sollte zuerst eine Evidenz-Inventur aufbauen — Manifeste, Lockfiles, verifizierte Build-, Test- und Run-Kommandos, Runtime-Pins in Containern und CI sowie externe Contracts — und jede Aussage als dokumentiert, abgeleitet oder unverifiziert kennzeichnen, bevor eine Zielarchitektur gewählt wird. Die Behandlung erfolgt komponentenweise in der Reihenfolge keep, upgrade, swap, wrap, rewrite; ein disruptiverer Schritt braucht Belege wie eine ungepatchte Schwachstelle, eine unter der Ziel-Runtime brechende Dependency oder ein messbar verfehltes Reliability-Ziel, nicht bloss Alter. Ein zeitlich begrenzter Feasibility-Check entscheidet zwischen "Verhalten erfassen, dann upgraden" und "zuerst einen kleinen modernen Slice bauen"; das öffentliche GitHub-Copilot-Agent-Skill doc-and-modernize kodiert dazu fünf Safety-Level von L0 (kein Regressionsnetz, Code und Doku als Spezifikation) bis L4 (CI-Gate aus Lint-, Unit-, Behavior- und E2E-Checks im vereinbarten Scope). Im PiggyMetrics-Fall (Java 8, Spring Boot 2.0.3, Spring Cloud Finchley, Zuul, Hystrix, spring-security-oauth2) zeigten zwei Probes mit JDK 8, dass das Config-Modul kompilierte und von 14 Tests fünf liefen, während neun an einem HTTP-403-Download von embedded MongoDB und einem i386-Binary scheiterten — daraus folgte Testcontainers als grüne Baseline, dann Java 21 mit Spring Boot 3.3, Spring Cloud Gateway, Resilience4j und Spring Authorization Server, wobei die Modulzahl von neun auf sieben sank. BrowserQuest wanderte von Node 0.4.7 auf Node 22 bei erhaltenem Canvas-Renderer, Pathfinding, Protokoll und Game-Loop-Modell, DOOM behielt Renderer, 35-Hz-Simulationsmodell und WAD-Format und tauschte X11-Video und OSS-Audio gegen SDL2, und ADempiere wurde auf JDK 21 mit XFire-zu-CXF- und Jakarta-Migration sowie erhaltener SOAP-Contracts gehoben — dokumentiert mit 30 gemergten Modernisierungs-PRs und 102.587,72 rekonstruierten Copilot-Credits bis zum ersten abgenommenen portablen Demo, ohne Anspruch auf vollständige Modernisierung.

A first look at Muru
21.11.2026
Muru lässt sich in drei Betriebsarten starten — Development Mode, Daemon für Server-Hosting und Container —, denen dasselbe Prozessmodell zugrunde liegt, sodass sich Entwicklung und Produktion gleich verhalten. Installiert wird nur das in Rust geschriebene Einzelbinary muructl (etwa per uv tool install muructl, alternativ pipx oder pip); die Python-Runtime-Bibliothek muru lädt muructl beim ersten Lauf passend zur Python-Version in den User-Cache, ins Projekt wird nichts geschrieben. Muru ist noch Alpha, es existieren nur Pre-Releases, unterstützt werden Linux und macOS auf CPython 3.11 oder neuer einschließlich der free-threaded Builds. Beim Start importiert ein Host-Prozess die Anwendung einmal, Worker werden davon geforkt, wobei Muru den Import vor dem Forken auf Ressourcen wie Datenbankverbindungen oder Threads prüft, die einen Fork nicht überleben. Das Access Log trennt die Wartezeit auf einen freien Worker-Thread (queue) von der Zeit im Anwendungscode (app) und gibt Worker-Nummer und Request-ID aus, letztere auch als X-Request-ID zurück an den Client; Fehler erzeugen im Development Mode Tracebacks in Response und Konsole (für JSON-Clients als application/problem+json nach Problem Details), beenden aber nie den Worker. Jede Codeänderung löst einen Auto-Reload aus, der einen neuen Host samt Workern als nummeriertes Release parallel zum laufenden startet, den Traffic erst nach dessen Bereitschaft umschaltet und bei fehlgeschlagenem Import auf dem alten Release weiterläuft — derselbe Mechanismus, auf dem der Daemon Zero-Downtime-Deploys, Blue/Green, Canaries und Rollbacks aufbaut. Flask und Django laufen ohne Anpassungen, etwa muructl run app:app oder DJANGO_SETTINGS_MODULE=mysite.settings muructl run mysite.wsgi:application.

Muru: HTTPS in development
21.11.2026
Muru liefert Entwicklungsservern HTTPS über das Flag --https: Der Run lauscht dann zusätzlich auf Port 8443 neben HTTP auf 8080 und erzeugt automatisch ein Zertifikat, das über die lokal installierte mkcert-Autorität ausgestellt wird, sofern mkcert -install gelaufen ist — andernfalls fällt es auf ein selbstsigniertes Zertifikat zurück und erklärt, wie es zu vertrauen ist oder wie mkcert nachzuinstallieren ist. Muru: how it fits together
21.11.2026
Muru zerlegt eine Anwendung in vier Rollen: die in Rust geschriebene Edge, die TLS, HTTP/1.1 und HTTP/2 spricht, Routing, Static Files, Kompression und Fehlerseiten übernimmt und nie Python ausführt; den Python-Host, der die Anwendung einmal importiert und Worker forkt, selbst aber keine Requests bedient; die Worker als Python-Interpreter mit bereits geladenem Code plus dünner Rust-Schicht, die WSGI auf Threads und ASGI auf dem Event Loop bedient; und den Controller, der Releases und Hosts steuert und nie auf dem Request-Pfad liegt. Die Edge beantwortet Requests selbst oder wählt nach Traffic-Policy ein Release und darin den Worker mit den wenigsten in-flight Requests; wartende Requests landen in einer Queue in der Edge, was die queue-Zahl im Access Log erklärt. Zum Worker läuft die Übergabe über den Unix-Socket-basierten Worker Link, auf dem keine HTTP-Texte, sondern bereits geparste typisierte Nachrichten samt gestreamtem Body übertragen werden; Antwort-Chunks werden gebündelt, Backpressure bis zur Anwendung durchgereicht, Request-Bodies erst bei Bedarf gelesen und Dateien direkt von der Edge ausgeliefert. Der zusätzliche Hop kostet eine weitere Kopie jedes Bytes und einige zehn Mikrosekunden pro Request bei Prozessen auf derselben Maschine, was neben der Laufzeit typischer Python-Webanwendungen verschwindet; der eigentliche Gewinn ist, dass Edge und Python-Prozesse unabhängig voneinander ersetzt werden können und mehrere Releases, notfalls auf verschiedenen Python-Versionen, parallel laufen. Ein Release ist eine unveränderliche Kombination aus Code, Python-Version, Settings, Host und Workern; ein Reload startet eine neue Release daneben und schaltet Traffic erst um, wenn sie bereit ist, sodass ein fehlgeschlagener Import die alte weiterlaufen lässt, und dasselbe Routing trägt Blue/Green-Deploys, Canaries und Rollbacks. Im Daemon-Betrieb liegen Controller, Admin-API und Store in einem langlaufenden Prozess, die Edge läuft separat und übernimmt beim Austausch die Listening-Sockets, sodass Daemon-Neustarts und Edge-Wechsel keinen Traffic unterbrechen; in einem Container startet muructl serve Edge, Controller, Host und Worker im Hauptprozess. Das ist der bewusste Kontrast zu Apache und mod_wsgi, wo der Parent-Prozess den Lebenszyklus aller Children besitzt und jede signifikante Änderung einen Apache-Neustart erfordert.

Muru skaliert Python-Anwendungen in zwei Stufen auf null: Bei min_workers = 0 entfernt der Daemon nach idle_reap_after (Standard zehn Minuten) den letzten Worker, lässt aber den Host laufen, der die Anwendung per import-once/fork-many bereits importiert hat — der nächste Request wird dann per Fork in rund 5 ms bedient. Ein zusätzliches host_idle_timeout stoppt auch den Host, sobald alle Workergruppen eines Releases entsprechend lange auf null stehen; der nächste Request zahlt dann den vollen Import (im Beispiel 3,3 s bei künstlich auf drei Sekunden gestrecktem Import). Anders als Gunicorn, uvicorn oder granian, die ihre Worker durchlaufen lassen, und anders als mod_wsgi, dessen inactivity-timeout den Prozess samt Neuladen der Anwendung neu startet, kollabiert der Wiederanlauf hier auf einen Fork, solange der Host existiert. Reicht der queue_timeout (Standard 5 s, im Test 2 s) nicht für den Import, antwortet das Edge mit 503, reason cold_start_timeout und Retry-After: 1, während der Host weiter startet. Ein node-weites [daemon.budget] workers = 6 (Memory- und CPU-Limits analog, unter systemd aus MemoryMax/CPUQuota abgeleitet) deckelt die Worker über alle Releases, wobei Wake-ups aus dem Null-Zustand das Budget überschreiten dürfen — laufende Worker werden nie verdrängt, stattdessen stoppt der Daemon retained Releases (Deploys behalten die Vorversion 30 Minuten) älteste zuerst, und bei konkurrierenden Skalierungen entscheidet priority; Releases mit gRPC-Mount brauchen dauerhaft mindestens einen laufenden Worker, da das Routing über die registrierten Services läuft.

Muru: tracing in the toolbar
21.11.2026
Muru ergänzt seine Entwicklungstoolbar um Tracing über wrapture, aktiviert per tracing = true und [[tool.wrapture.instrument]]-Einträgen für flask, sqlite3 (mit statement = true) und urllib.request in pyproject.toml; Tracing erfordert Python 3.12 oder neuer und lässt sich über muru.local.toml nur lokal einschalten, bei fehlender oder fehlerhafter Konfiguration startet die Anwendung ungetract mit einer Warnzeile. Die neuen Panels Trace, SQL und Outbound zeigen den Operationsbaum pro Request sowie nach Statement gruppierte Queries und nach Methode, Host und Pfad gruppierte ausgehende Aufrufe, wobei Pfadsegmente mit Zeilen-IDs als {id} normalisiert werden; damit lässt sich das N+1-Muster im Beispielshop direkt erkennen, wo acht Bücher acht Autoren-Queries und acht Stock-Aufrufe auslösen. Hints schlagen an, wenn ein Statement oder Endpunkt fünfmal oder häufiger pro Request läuft, oder wenn eine einzelne Query bzw. ein Call mindestens ein Viertel der Request-Zeit und wenigstens 10 ms belegt. Für Anwendungen ohne Framework-Instrumentierung, etwa reine WSGI- oder ASGI-Callables, wickelt tracing_middleware = true den Entrypoint in wraptures Request-Middleware — nicht zu kombinieren mit vorhandener Framework-Instrumentierung. Architektonisch wendet der Host die Patches vor dem Import der Anwendung an, während Sinks erst nach dem Fork in jedem Worker starten; Datei-Sinks brauchen {pid} im Pfad, unter muructl serve und dem Muru-Daemon entfällt die Toolbar und es bleibt nur der Aufwand der konfigurierten Sinks, in Produktion üblicherweise der Export an einen OpenTelemetry-Collector.

Muru: working with Kubernetes, not around it
21.11.2026
Muru lässt sich unter Kubernetes so betreiben, dass es Plattform-Funktionen nutzt statt sie nachzubauen: Das Deployment läuft mit zwei Replicas und je zwei Workern à vier Threads, passend zu den Limits von 2 CPUs und 1Gi Speicher, die Probes zeigen auf den nicht über den Service exponierten Admin-Port 9090, JSON-Logs erhalten Pod-, Namespace- und Node-Namen über die Downward API, und die Pods laufen unter dem restricted Pod Security Standard mit read-only Root-Filesystem, in dem nur /run/muru und /tmp beschreibbar sind. Statt eines preStop-Hooks übernimmt MURU_SERVE_SHUTDOWN_DELAY (5s) die Drainage: Bei SIGTERM schlägt /readyz sofort fehl, der Listener bleibt offen und beantwortet neue Verbindungen mit Connection: close; im Test mit acht Keep-Alive-Verbindungen und einem Rollout-Restart gab es mit Delay null Fehler, ohne Delay viermal ConnectionRefusedError, während Gunicorn und uvicorn den Listener sofort schließen und ihre Graceful-Timeouts erst danach greifen. In-Place-Resizes nutzen das seit Kubernetes 1.35 stabile resize-Subresource mit resizePolicy restartPolicy: NotRequired, Muru liest die geänderten cgroup-Limits beim nächsten Memory-Check neu und warnt, wenn die Worker nicht mehr zu den Ressourcen passen; bei RestartContainer, etwa nach einer fehlgeschlagenen Liveness-Probe, ist failureThreshold: 1 auf der Readiness-Probe erforderlich, weil der Default von drei Fehlversuchen à 2 Sekunden bis zu 6 Sekunden braucht und damit länger dauert als die 5-Sekunden-Drainage (im Test zehn ConnectionRefusedError). Autoscaling läuft über muru_capacity_utilisation, den über 30 Sekunden gemittelten Anteil belegter Worker-Slots, den Prometheus und der Prometheus-Adapter als Pods-Metrik bereitstellen; mit Ziel 70 Prozent skalierte das Deployment unter 24 Threads Last in unter einer Minute von zwei auf vier Pods, während kubectl top nur rund 10m CPU pro Pod zeigte, also etwa 2 Prozent der angeforderten 500m, weshalb ein CPU-basierter HPA bei zwei Pods geblieben wäre — nach Lastende ging es nach der Stabilisierungswartezeit von fünf Minuten auf zwei Pods zurück. Als Alternative nennt der Artikel die Queue-Wartezeit aus dem Request-Histogramm (95. Perzentil 0,457s), die sich als External Metric oder über KEDA auswerten lässt. Migrationen laufen als Job mit muructl command run migrate aus dem neuen Image, backoffLimit 0 und kubectl wait auf Complete, bevor das Deployment-Image aktualisiert wird; dieselbe Command-Definition samt Timeout nutzen auch kubectl exec und der Daemon.

Twenty years of mod_wsgi, and what comes next
21.11.2026
Zwanzig Jahre nach Beginn der Coding-Arbeiten im Dezember 2006 pflegt Graham Dumpleton mod_wsgi weiter und baut parallel ein neues Hosting-System namens Muru. Die ursprüngliche Entscheidung für Apache erklärt sich aus dessen Allgegenwart: Die WSGI-Spezifikation existierte, aber es gab keinen etablierten Produktionsweg dafür — nginx war außerhalb Russlands kaum auf dem Radar, gunicorn kam erst Jahre später, und mod_python war nicht um WSGI herum gebaut. Genau das wurde zur Grenze: Apache besitzt den Lebenszyklus aller Kindprozesse, die Anzahl der Daemon-Prozesse ist per Konfiguration fix, jede Änderung erfordert einen Apache-Neustart, und lastabhängiges Skalieren oder Rollouts ohne abgebrochene Requests ließen sich innerhalb des Moduls nie umsetzen. Muru ist kein Apache-Modul und kein reiner WSGI-Server, sondern hostet WSGI-, ASGI- und gRPC-Anwendungen auch gemischt in einem Deployment, erlaubt Request-Übergaben zwischen WSGI und ASGI (etwa um Websockets in bestehende Anwendungen zu bringen) und macht Rollout, Routing, Health-Checks und Restarts ohne Request-Verlust zum Standard statt zur Eigenbaulösung. Hinzu kommt Python-spezifisches Wissen — GIL und die Prozess-versus-Thread-Wahl, lange Importzeiten bis zur Bereitschaft, schleichendes Speicherwachstum — dessen Metriken wie Thread-Auslastung und Wartezeiten direkt in Kapazitäts-, Prozess- und Routing-Entscheidungen zurückfließen. Der Code entsteht überwiegend mit KI-Werkzeugen, Architektur und Review liegen bei Dumpleton; Muru ist noch in Entwicklung und bewusst nicht öffentlich verlinkt, mod_wsgi wird nicht eingestellt, und eine Postserie soll lokale Entwicklung, Deployment auf Host oder VM sowie Container- und Kubernetes-Betrieb abdecken.

How to build a software factory you'll actually use
24.11.2026
Warp beschreibt eine Software Factory als Automatisierungsschleife in der Cloud, die Agenten orchestriert, um Software über die Zeit Stück für Stück besser zu machen. Statt einen Issue-Backlog einfach durch einen Agenten zu drücken, definiert man den Ablauf als YAML-Blueprint mit benannten Stages, expliziten inputs und outputs, ausgelagerten Markdown-Prompt-Dateien und separaten Workern als je eigenen Sandboxes mit eigenem Kontextfenster — im Beispiel ein foreman für die Nutzerkommunikation und ein builder für den Code, was den gesamten Workflow visualisier- und debugbar macht. Als Trigger genügt ein GitHub-Issue-Label (factory); für kleine, klar umrissene Änderungen an einer Electron-App kostet ein Durchlauf mit einem Open-Weight-Modell unter einem Dollar pro Issue. Für mehrdeutige Anforderungen schiebt man triage- und spec-Stages vor die Implementierung: Der Agent stellt Rückfragen, sammelt Produktentscheidungen und committed die Spec als Code, deren Validierungsabschnitt später als Prüfliste für die Implementierung dient. Zur Verifikation erhalten die Worker Computer Use in der Sandbox (App-Start via MARKY_DESKTOP_ENABLE_CDP=1 pnpm dev:desktop, Interaktion bevorzugt über das Chrome DevTools Protocol) und hängen Videoaufzeichnung plus Screenshots als "Visual proof" an den PR. Ein Merge-Risk-Skill (warp.dev/merge-risk) bewertet Alignment, Impact, Verification, Rollback-Cost und Error-Detection zu einem Low/Medium/High-Score und sollte bereits vor dem Öffnen des PRs laufen, damit der Agent Risiken wie fehlendes Error-Logging früh beheben kann; geplant sind unter anderem Benchmarks verschiedener Code-Review-Varianten vor dem PR, ein Research-Agent mit separatem Kontextfenster und eigene macOS-Runner für native iOS-Apps.
