Building the Agent Host Protocol for sessions that continue across devices
17.11.2026
Das Agent Host Protocol (AHP) ist ein offener Standard, der zuerst in VS Code entstand und inzwischen GitHub-weit Agentensitzungen über Editor, Copilot-App, Mobile und Cloud hinweg fortführt: Ein Server ist Arbiter eines reducer-basierten Zustandsobjekts, Clients senden Aktionssequenzen, die den Zustand mutieren oder Seiteneffekte wie das Absenden einer Chat-Nachricht auslösen, was Reconnect, Replay bei schlechten Netzwerkbedingungen und konkurrierende Mutationen mehrerer Clients abdeckt. Das Protokoll gliedert sich in URI-identifizierte Channels — root, session und chat sind Pflicht, optionale Channels decken Terminal-Support, MCP-Erweiterungen und OTel-Reporting ab — und kodiert bewusst kein Agentenverhalten, weil sich dieses Feld zu schnell entwickelt; MCP-ähnliche Escape Hatches über Custom Methods und _meta-Felder erlauben Erweiterungen. Für VS Code wurde die über drei Jahre gewachsene Copilot-Chat-Extension mit mehr als 400.000 Zeilen TypeScript (ohne Tests) durch einen neuen Harness auf Basis des Copilot SDK ersetzt, während GitHub seinen Agent Host unabhängig in Rust implementierte, um Cloud-Betrieb und abweichende Infrastruktur- und Security-Anforderungen abzubilden; die zwei Implementierungen dienten zugleich als Praxistest für die Portabilität des Protokolls. Bibliotheken gibt es in Rust, TypeScript, Kotlin, Swift, .NET und Go; VS Codes Host lässt sich mit code agent host starten, Endpunkte mit code agent endpoints ausgeben, und die Copilot-App nimmt Hosts über Experimental > Direct Connections sowie Environments > Add Agent Host Protocol Host entgegen.

Data Contracts
18.11.2026
Data Contracts beschreiben Inhalt und Zusagen eines Datensatzes maschinenlesbar, verifizierbar und versioniert und machen Datensätze damit sowohl für Menschen als auch für AI-Agents belastbar nutzbar. Als De-facto-Standard etabliert sich die Open Data Contract Standard (ODCS) des Bitol-Projekts der Linux Foundation, aktuell in Version 3.2.0, die Schema, Quality Rules (SQL oder Library), SLA-Properties wie Freshness und Retention, Ownership, Support-Kanäle, Terms of Use, Server-Definitionen, Rollen, Preise und seit 3.2 einen AI-Context-Block mit Instruktionen, Constraints und verifizierten Statements definiert. ODCS startete 2023 als PayPals Data Contract Template, wurde als ODCS 2.2 Gründungsstandard von Bitol, verlor mit 3.0 (2024) die PayPal-Spezifika, wurde 2025 mit 3.1 und nativer CLI-Unterstützung mit der konkurrierenden Data Contract Specification zusammengeführt und 2026 um den AI Context erweitert; der Thoughtworks Technology Radar führt ODCS auf Adopt. Darauf aufbauend beschreibt die Open Data Product Standard (ODPS, v1.1.0) Datenprodukte, deren Input- und Output-Ports auf ODCS-Contracts verweisen, wobei einseitig publizierte Contracts und bilaterale Access Agreements mit Ablaufdatum (RFC für einen Open Access Agreement Standard, OAAS) strikt getrennt bleiben. Contracts gehören ins Git-Repository neben den Pipeline-Code und in die CI/CD-Pipeline; die Data Contract CLI mit über einer Million Downloads pro Monat (Radar-Bewertung Trial, November 2025) bietet dafür lint, breaking, ci, test und publish, während die Versionierung SemVer folgt und ein Major-Bump einen neuen Datensatz, ein neues Topic oder mindestens forward-kompatible Schema-Evolution verlangt. Der Nutzen – Pipeline-Generierung per Coding-Agent, verlässliches "Chat with your data", automatische Erkennung von Breaking Changes – rechtfertigt die Kosten nur bei Team-übergreifenden Schnittstellen, idealerweise als Ports von Datenprodukten, nicht als flächendeckende Einführung über allen Datenbeständen.

Deterministic Simulation Testing
17.11.2026
Deterministic Simulation Testing ersetzt echte Uhr, Netzwerk und Storage durch simulierte Komponenten, die ein single-threaded Execution Loop per tick()-Aufruf vorantreibt, wodurch sich harte Ausfälle und Grauschäden wie Latenzspitzen reproduzierbar testen lassen. Unmesh Joshi, Distinguished Engineer bei Thoughtworks, demonstriert das Verfahren an einem Quorum-Key-Value-Store mit der Java-Bibliothek Tickloom, deren Design auf FoundationDB (deterministischer Scheduler, C++-Koroutinen) und TigerBeetle (tick-getriebene Single-Thread-Architektur mit tick_ms = 10) zurückgeht; etcd arbeitet ebenso mit logischen Ticks (100ms-Ticker, 10-Tick-Wahltimeout von einer Sekunde). Die vier Quellen der Nichtdeterminiertheit — Systemuhr, Thread-Scheduling, Netzwerk- und Disk-Timing — werden hinter Interfaces wie Network, FileIO und Clock gekapselt, Timeouts zählen Ticks statt Wanduhrzeit, und eine gesäte PRNG steuert die Fault Injection (Standardwerte: 40 Prozent Request-Wahrscheinlichkeit, 8 Prozent Fault-Wahrscheinlichkeit, Netzwerk-Heilung alle 40 Ticks), sodass ein Seed exakt dieselbe Ausführung reproduziert. Wie bei Jepsen wird die client-sichtbare History aufgezeichnet und von einem ConsistencyChecker auf Linearisierbarkeit geprüft; Fast-Forward lässt Läufe, die live Stunden benötigen, in Sekunden durchlaufen. Sechs strikte Coding-Regeln — keine System-Clock, keine ungesäte Zufälligkeit, keine Threads oder CompletableFuture, kein direktes Netzwerk- oder Disk-I/O, keine Iteration über ungeordnete Collections, keine Cross-Thread-Callbacks über die Architektur-Naht — werden per ArchUnit-Fitness-Function und Thread-Confinement-Checks in TickCompletableFuture durchgesetzt. Der Ansatz verlangt Architekturinvestitionen im Voraus, zahlt sich aber aus, weil IO-lastige Systeme von single-threaded asynchronem, gebatchtem I/O profitieren (wie Redis, FoundationDB und TigerBeetle); wo ein Umbau nicht möglich ist, bietet die kommerzielle Plattform Antithesis deterministische Simulation auf Hypervisor-Ebene.

Introducing staged publishing on NuGet.org
17.11.2026
NuGet.org führt Staged Publishing ein, verfügbar für alle Paketpublisher: Pakete durchlaufen nach dem Upload die vollständige Validierung (Malware-Scan, Signatur- und Repository-Signierungsprüfungen), bleiben aber bis zur expliziten Promotion durch einen autorisierten Maintainer privat und erscheinen weder in Suchergebnissen noch in Restore-Vorgängen. Staging ist Opt-in, bestehende dotnet-nuget-push-Workflows laufen unverändert weiter, und anders als bei unlisted Packages, die sich per exakter Version weiterhin wiederherstellen lassen, ist gestagter Inhalt für Konsumenten überhaupt nicht verfügbar — einen privaten Restore-Feed bietet Staging allerdings nicht. Verwandte Pakete lassen sich in Staging Groups bündeln und als Satz promoten; die Gruppen-Promotion ist jedoch nicht atomar, Pakete werden also zu unterschiedlichen Zeitpunkten restorable. Für die Absicherung empfehlen die Autoren Staging-only-Credentials beziehungsweise auf Staging beschränkte Trusted-Publishing-Policies, sodass eine kompromittierte Pipeline nur Inhalte zur Review einreichen, aber nichts direkt veröffentlichen kann; die Promotion selbst erfolgt ausschließlich über die Website mit 2FA-aktiviertem Konto, nicht per CLI. Das .NET 11 RC2 SDK unterstützt bereits dotnet package stage push inklusive --group-Parameter (Gruppen werden bei Bedarf automatisch angelegt), Listing- und Gruppenverwaltungsbefehle folgen in einem späteren SDK-Update; nicht promoteter Staging-Inhalt läuft ab.
